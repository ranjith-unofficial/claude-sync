⚑ Things that need a decision, not just a read

Four places where the source document contradicts itself — genuinely different mechanisms describing the same job, not just old-vs-new. Worth resolving with Utkarsh/eng before anyone treats one of these as ground truth.

1. There are four different Brief-ranking formulas in this document

Master PRD §4.4 (the doc's own "canonical" spec) describes a 3-stage model: editorial hand-pins the lead story → an LLM ranks the rest of the candidate pool → a deterministic tracked-company/sector boost re-orders on top. The standalone Article Ranking Logic tab — which reads like a locked, precise spec (exact weights, a real 90-day popularity dataset) — describes something else entirely: a pure deterministic formula (TopicAff + SectorAff + Popularity, no LLM step at all). The archived Brief_Personalization_logic doc has a third mechanism (5-tier Editorial Importance score + "Full-Match Primacy" priority group), and WIP's v0_Brief Personalization has a fourth (per-ICP Signal Score tables). None of these four fully match.

This doc places the standalone Article Ranking Logic tab in Production, since it reads as the most current and precisely specified — but that's a best guess from the text, not a confirmed fact. Worth a direct check with eng on which formula is actually implemented.

2. Notification logic is split across three non-overlapping documents

The Master PRD §8.5 defines what gets pushed and the fatigue rules (grouping, caps, quiet hours). The standalone Notification Permissions & Re-Ask Logic doc defines the ask flow (first prompt, re-ask cooldowns) — no content rules. The WIP Notification Strategy PRD defines a specific timed reminder cascade (7:30am → 11:30am → 6pm) and a full Brief state machine that appears nowhere else. These three don't conflict, but no single current document has the whole picture, and the WIP doc's exact reminder times aren't confirmed as still-current anywhere else.

3. Two independent events-fix audits, not fully reconciled

New_event_sheet_Changes flags architecture-level bugs (no PostHog/Customer.io person profile for anonymous users, so every logged-out property update fails silently; properties bundled incorrectly; email leaking into event payloads). Events Sheet — Consolidated Change List (the most recently named, last tab in the doc) flags a different, non-overlapping set of fixes, including the Customer.io anonymous→login merge bug. They read like two separate audits done at different times — the Consolidated list does not supersede the first one's P0 items.

4. "App V2" is not an empty tab — it's a live 19 Aug scope doc

The top-level "App V2" tab looked structurally empty on a first pass (no markdown headings), but it actually contains a full, dated (2026-08-19) 11-workstream scope document with owners and priorities — one of the most current things in the whole file. It's placed under Next Sprint here.

Inc42 App — v1 PRD (Final v3)

Owner: Utkarsh · Status: canonical — single source of truth for v1
Canonical

The app in one page: Brief (a finite, personalized morning brief that ends), Explore (~30K-article archive + Datalabs' 70K-company graph, pull-only), Watchlist (what you track + its movements), Company profiles (glanceable Datalabs depth). Audience: Founder · Investor · Startup Operator · BD & Partnerships · Other. Because it's a native app that can't hotfix, everything tunable — caps, cadence, ranking, copy, taxonomy, flags — lives in server-side remote config, with a force-update/min-version gate as insurance.

Design principles

  • Finite before infinite — opens to the Brief, ends with "Done for today," no feed continuation
  • Depth on demand — headline → Decode → full article → entity profile, each by choice
  • Watchlist is the personalization engine, not an algorithm — explicit choices, no behavioral feed
  • Shown, not narrated — visible "relevant because…" attribution, no covert personalization
  • Signal-dense cards, not image-forward; must beat inc42.com mobile; everything is Inc42 (no external aggregation)

Information architecture

3 bottom tabs — Brief · Explore · Watchlist — plus a global search and account avatar in the top bar (neither is a tab, no hamburger menu). Article reader is a full-screen modal from anywhere; company profile is a shared tap-target; Ask Inc42 is a mode, not a tab (dormant in v1).

Onboarding & auth

5 screens (~45–75s): welcome → role/ICP → 7 clubbed sector groups (pick ≤3, locked 2026-07-04) → watchlist seeds (≥1 required, 3 recommended, skip-with-friction) → done. No "Pick Topics" step in v1. Anonymous use is allowed; a soft sign-in sheet triggers only on a gated action (follow, ~5 profile views, 3rd save) and merges local data. iOS must offer Apple + Google + email (Guideline 4.8 — Google-only gets rejected); Android ships Google + email.

Brief (the hero)

A finite, relevance-ranked stack of 6–8 cards. Mon–Fri daily + Sat weekly recap + Sun off, pushed ~7–8am local. Resting state is a cover screen; opening it enters a full-screen swipe-up story flow, one card per screen, ending at Done. Card anatomy: signal-type tag, headline, byline, 3-bullet Smart Brevity body (or a deterministic funding block), ⭐ watchlist hit, 🎯 + "relevant because…" label, ✨ Decode, a free suggested-question chip, Read Full Story.

Cover rules: the daily edition line is a real editorial hook, not a table-of-contents label ("Late-stage fintech is back: two mega-rounds in one week."); a "relevant to you" pre-glance surfaces when boosted cards exist; the greeting must match local time or be dropped; a dry, factual missed-day recovery line ("You missed Thursday. It's still here.") — no guilt register.

Editorial governance: the headline + 3-bullet summary are written by editorial alongside publishing the source article — same hand, same moment, no net-new daily workload. The cover/push edition line is the one genuinely net-new editorial input per day. The LLM's v1 jobs are ranking and on-demand Decode, not summary generation — LLM-assisted bullet drafting is a v1.1 option.

Streaks (mechanic locked 2026-07-04; reward model locked 2026-07-05)

Earned on completing the brief (not opening). No dedicated streak push — folds into the completion nudge. Sat counts, Sun never breaks it, no paid streak-repair ever. Daily surface = a substance counter (cover row + Explore strip): Day N · tier · X stories · Y companies tracked. A rare full-screen milestone fires only at Day 1/7/30/100 — payload is substance + tier promotion only, no share/unlock (reserved for a later rewards layer). Tiers — Reader → Regular → Insider → Ecosystem Native — are sticky: a streak reset never strips the tier, only the daily number.

Explore

The archive + company graph, pull-only — not a discovery feed (the Brief owns "today"). Layout: search → Today's Datalabs signals rail (collapsed) → Articles/Companies switch → sub-nav pill strip → feed → recently viewed. Any industry tap anywhere lands on a Sector landing — Explore pre-scoped to that one sector, not a heavy dashboard. 17 canonical sectors shared between editorial tags and Datalabs' company_sector.

Watchlist

The Following + Saved surface. Track only Companies + Sectors in v1 (people/funds need profiles → v1.1+, investor before person). Free caps ~15 companies + 5 sectors; hitting a cap shows a soft "more depth coming," never a hard wall. Recent Alerts = last 20 in view, 90-day rolling history behind "See all."

Company entity profile

Order: Header → Funding → People → On Inc42 → Ask-stub (dormant). Launch depth locked = V2+ (V2 Deep + headline historical P&L — YoY Revenue/Expense/Profit-Loss, ~3–5yr trend): a deliberate, accepted partial overlap with Datalabs Pro's web product, traded for app wow-factor, while full balance sheet / expense line-items / ratios / cap table / valuation history stay Pro-reserved. The tier boundary is always a server-side field mask, never baked into the client.

Cross-cutting surfaces

Decode vs. "In 30 seconds": Decode is always a live, user-triggered AI explainer (brief cards, Explore Decode action, profile Ask-stub) — soft-capped, non-blocking, always teaser-and-routes to the article. The pre-written one-line card summary is a separate, editorial/deterministic thing named "In 30 seconds" (provisional wording) — explicitly not Decode, to protect the "not an aggregator" line. "Signal" stays reserved for the data vocabulary (signal-type tags, the Datalabs signals rail, the data team's Signal Engine) and is never used for the AI explainer.

Success metrics (v1)

D7 ≥30% · D30 ≥15% · Brief completion ≥40% (= final card reached) · push opt-in ≥55% · watchlist completion ≥30% · Decode usage ≥15% of opened stories · search/DAU ≥0.3 · Datalabs profile views/DAU ≥0.2 (M1) → 0.5 (M3) · crash-free ≥99.5%.

Rollout & risk

(a) 48-hour TestFlight founding-reader wave (top ~2K Daily Brief openers), then (b) staged Play rollout 10%→50%→100%, gated on crash-free rate and brief-completion. Key risks: editorial capacity (largely absorbed — the only true net-new work is the daily edition line); the Explore hybrid search backend is unverified and its 20-query reality check is launch-gating; India Android OEM background-kill can silently drop the Morning Brief (instrumented from day one, see Launch Infra).

Article Ranking Logic — Personalized Daily Brief

Likely current
See flagged conflict #1This reads as the most precisely specified ranking doc in the file — but it describes a different mechanism than the Master PRD's own §4.4. Treat as probably-current, confirm with eng.

Two signals from the user (Followed Topics, Followed Sectors) combine with per-article Development_Type and Company_Industries, plus two fixed popularity tables built from a real 90-day co-read study (a crowd-level prior — News/Consumer sit at 1.0, everything else scaled beneath).

TermFormula
TopicAff1.0 if article's topic ∈ followed topics; else max affinity; 0 if none set
SectorAffΣ (parent multiplier × parent affinity) across each unique parent sector in the article
Pop½·topicPopularity + ½·sectorPopularity
Score1.0·TopicAff + 0.6·SectorAff + 0.15·Pop

Ranked by score then recency. Editorial Override: an "App Featured Article" flag (default No) places a story above all ranking rules entirely; multiple featured articles tie-break by publish time. Edge cases are all handled by the same formula — no topics set, no sectors set, neither set, article missing a field — everything degrades gracefully to popularity + recency rather than breaking.

Streak & Rewards

One count per active day regardless of how many briefs are completed that day; a missed calendar day resets the streak to 0, restarting from 1. A day is marked active the moment the user completes their first brief. Badges and reader levels are one-time and permanent — climbing back to a milestone day after a reset does not re-award an already-earned badge. The calendar view marks active days, today, and missed days, plus a monthly "% days active" summary.

Account Deletion

Owner: Ranjith · Surfaces: iOS, Android, Web, Datalabs

Driven by Apple 5.1.1(v) (in-app deletion, not deactivation-only), Google Play's public-URL requirement, and DPDP's right-to-erasure (30-day completion window). States: active → pending_deletion (restorable 72 hours, signed out everywhere) → deleted (permanent).

Deleting on any platform signs the user out of iOS, Android, Web, and Datalabs. Web deletion lives at inc42.com/delete-account, usable without the app (login itself serves as identity verification). Sign in with Apple tokens are revoked only after permanent deletion at Day 3 — revoking immediately would break restoration; never revoking risks App Store rejection.

The instant deletion_pending = true, the user is excluded from every newsletter, campaign, push, and automated journey — every marketing campaign must filter on this flag. On permanent deletion, Customer.io, PostHog, Firebase, and Singular all receive deletion requests.

Still openWhat happens to a Datalabs Pro/Team subscriber's billing on deletion (terms currently say deletion doesn't cancel payment obligations); whether Team admins can orphan seats by deleting; whether restoration on login should be automatic + a confirmation toast (recommended).

Inc42 App — Privacy Policy

Ideope Media Pvt. Ltd. licenses the App exclusively to Inc42 Plus Media Pvt. Ltd. ("Inc42 Group"). Covers two groups: App Users, and Listed Individuals — founders/executives whose name and designation only appear in company pages (no work email, phone, or LinkedIn), governed jointly with a separate Contact Data Policy.

What's collected

From users: identity data, account data, onboarding preferences (role/sectors/topics), activity (saves, tracked entities, brief reads, streaks), support correspondence. No payment info is collected (no in-app subscriptions) and there's no user-generated content. Automatically: device info, a device-level ID generated on first open + advertising IDs where permitted, IP/network info, usage/search data, coarse IP-derived location only (no GPS), install attribution.

Legal basis & consent

DPDP has no GDPR-style "legitimate interest" basis — analytics runs on consent. Analytics/tracking begin firing from first open, including pre-account browsing, ahead of in-app consent controls that are still being built; until then, users can only limit tracking through device settings and the ATT prompt.

Rights, retention, breach

DPDP rights (access, correction, erasure, consent withdrawal, nomination on death/incapacity, grievance) via grievance+datalabs@inc42.com, or in-app deletion. Newsletter links open in Safari instead of the app. The Customer.io click-tracker redirect breaks Universal/App Links, because iOS checks the app association against the first tapped domain (the tracker, not in AASA) rather than the final destination. Brief Title, Push Notification & Image — Generation Logic

Owner: Ranjith · Reviewer: Utkarsh · Status: decisions closed

Every title and push is generated — nothing pre-written (statics go blind and kill CTR within days). One generation per sector/topic per day (not per user — rejected as 4,000 generations/day at 500 users), capped at ≤17 generations/day total. One model call returns 4 fields: title (60 char), subheader (70), push_title (32), push_body (100) — kept in one call specifically so the header and the notification never contradict each other.

At render, each user gets the highest-ranked sector/topic among what's actually in their delivered 8 articles that day — read from the real brief, not onboarding preferences alone, or the header can say "Fintech" over an ecommerce-heavy brief.

Image — locked

Featured article exists → its lead image. No featured article → editorial's uploaded poster for the day. Neither → default image. No lead_article_id, no separate image-selection logic needed — title and image agree by construction on featured days.

Flagged in the doc itselfThe topic ranking table (§2.5) was inferred from headlines, not a real CMS topic field — the export carried no topic column. Re-export with the actual Development_Type tag before locking those numbers. Separately, 17% of articles have no sector and surface only via the topic layer — the same tagging gap referenced in the v2 scope doc's sector-images blocker.

Notification Permissions & Re-Ask Logic

One native OS prompt only, fired once on the Brief page post-auth. After that, all re-asks are in-app soft-asks only (bottom sheet, "Turn on" / "Not now"). Re-ask triggers: following an entity while alerts are off ("Get alerts on {entity}?"), or a 2+ day gap with brief notifications off ("You missed {N} briefs"). Caps: 30-day cooldown between any re-asks, lifetime cap of 2 dismissals, never stack two asks in one session.

PRD — Inc42 Pulse (Social Intelligence) v2.0

Owners: Ranjith (product/AI) · Utkarsh (research/decisions) · Nityam (design) · Editorial · Status: draft for review, 30 Jul 2026
v2.0 combined

Inc42 reports what happened; Pulse packages what the ecosystem is saying about it — top LinkedIn/X posts from ~200 allowlisted ecosystem voices, filtered by an LLM, synthesized into 1–2 line summaries, 100% editorially reviewed before anything publishes. Not a feed: no comments, no user-generated content, no infinite scroll, no following individual people.

This version explicitly merges two earlier parallel drafts (Ranjith's product-mechanics PRD and a separate research/legal/supply-data track) — the reconciliation, not a replacement of either.

The framing pivot (§1.1)

Originally modeled as an efficiency job ("save time scrolling"). An independent 5-model review reframed it: three of five models read the real driver as status maintenance — knowing what matters, so you're not the one who missed it. That reframe is load-bearing: under a status framing, named voices become non-negotiable ("Nithin Kamath argued X" carries status; "an investor said X" doesn't), controversy beats consensus, and sharing becomes the product's actual point, not a vanity metric.

The doc's own honesty checkThe team's main disconfirming-demand evidence — a 0.046% pain-mention rate found by mining 77K posts — is explicitly called out as a weak instrument under the status framing, since people don't publicly admit to status anxiety. The doc's own conclusion: down-weight that null, don't treat it as real disconfirmation, and add a status-framed variant to any future user-research test. The premise stays formally ASSUMPTION — UNVALIDATED and gates on a Phase-2 research check.
Locked decisions
D1 name = PulseD2 Free teaser + Plus/Pro depthD3 LLM synthesis + 100% manual approval D6 matching = enrichment, not a gateD7 ~200-voice allowlist, sector personalized D8 quotes switchable behind a flagD9 phased cadenceD13 ship v1 on a sheet, not a custom app
How matching actually works (D6)

Measured over 60 days: only ~13% of quality ecosystem commentary corresponds to anything Inc42 already published — 86.5% is orphan, and the orphan half is the more differentiated half (87–92% absent from editorial vs. 26–73% for hard-news topics). So a story match is enrichment, not a gate: unmatched items flow to the Pulse section; matched items additionally power in-article Pulse.

Cadence (D9)

Phase 1 rides the morning Brief as 2–3 cards after the editorial cards — no new session, no new push permission, cut-off ~8pm the prior evening. Phase 2 is a dedicated evening edition (deliberately not morning, so it never competes with the Brief), starting ~6:30pm — a reachability decision, not a freshness one, since later sends are fresher but lose the audience. Graduation from Phase 1→2 requires ≥15% engagement of Brief-opening sessions sustained 4 weeks, ≥5 approved items on ≥85% of days, and no holdout regression.

Legal (§13) — the hardest gate

LinkedIn's User Agreement prohibits both scraping and use of scraped data (LinkedIn won a permanent injunction against hiQ on breach of contract); ingestion runs via Apify/twitterapi.io with no license or safe harbor. India's §52 fair-dealing copyright exception is a closed list (unlike the US's open factor test), and "reporting current events" is enumerated — synthesis is much stronger ground than reproduction. Quotes are being built behind a flag specifically because of this: ship synthesis-first, turn quotes on only if counsel clears rung 3 of a 4-rung format ladder. If counsel lands on rung 4 (per-voice consent), the doc explicitly says this PRD doesn't survive contact as written — it would need to descope to a 20–40-voice consenting editorial franchise instead.

Kill criteria

Engagement <5% of all Brief-opening sessions sustained 4 weeks, with reach ≥50% (people saw it and didn't want it) → disconfirms the demand hypothesis, folds supply back into editorial, no Phase 2.

AskInc42 Feature Flag Rollout Strategy (PostHog)

PostHog's React Native SDK is already live in the app project (146258), collecting since 1 Jul 2026 — but zero feature flags exist in that project today (2 legacy flags exist only in the unrelated DataLabs Web project). All rollout mechanisms needed (percentage rollout, sticky bucketing, person-property targeting, cohorts, individual dogfooding, multivariate) are already supported — no SDK work required, only flag creation.

Three React Native gotchas flagged for whoever builds this: flags cache indefinitely on-device (call reloadFeatureFlagsAsync() on every launch/foreground); bucketing can silently flip after login since distinct_id changes on identify(); and the first-launch flag read returns undefined before the initial /flags call resolves, so a naive truthy check can flicker the UI on cold start. Recommended rollout ladder: internal 100% → pilot 1% → 5% → 25% → 100%, with a server-side kill switch live at every stage.
